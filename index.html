01 Compile

From declared intent
to a pinned digest.

The compiler is offline and deterministic: it validates the resources, composes the semantic layers and writes a typed plan. That plan is the only thing the backend is allowed to read.

1

You describe the machine.

A workstation is a few small YAML files, not a script. It says which platform it is for and which profiles it includes; the platform says which base to start from and pins that base by digest.

workstations/deskos-core-centos-stream-10.yaml platformRef: centos-stream-10 profiles: [deskos-core, deskos-gnome, …] platforms/centos-stream-10.yaml bootc.image: centos-bootc:stream10 digest: sha256:98cb9980…

green the workstation · blue the pinned base

DeskOS reads it
2

DeskOS merges it and checks it.

Profiles are layers: foundation, organization, role, workstation. Lists add up. If two layers set the same thing differently, compilation stops and names both — there is no “last file wins”.

foundation organization role workstation
→
the plan "baseImage": "…@sha256:98cb9980…", "packages": ["firefox", "flatpak", …]

The plan is the full, checked recipe. Nothing else decides.

and writes the build recipe
3

The plan becomes a Containerfile.

That is the file podman builds. You never edit it: every line comes from the plan, so a change is a diff you can review before anything is built.

plan baseImage: centos-bootc@sha256:98cb…
same digest
Containerfile FROM quay.io/centos-bootc/ centos-bootc:stream10@sha256:98cb…

One fact, one place. Everything else in the file follows the same rule.

podman build
4

You get one bootable image.

The result is an OCI image with a digest. That digest is what a machine runs, what gets signed, and what the SBOM describes — not a tag that can move.

image@sha256:98cb…

bootc · signed digest · SBOM · scanned

YAML → plan → Containerfile → image. Every line can be traced back, and the same inputs always produce the same plan.

Containerfile
the recipe podman builds.
bootc image
a container that boots as a machine.
digest
the content address of the image.
Deterministic
Sorting and normalization are part of the plan; the same inputs produce the same bytes.
Offline
No network, no model, no service. Builds fetch; plans never do.
One writer
Facts come from resources. There is no script hook and no post-install command.
Reviewable
A change appears as a diff in plan.json and in the Containerfile, not as a runtime effect.

02 Platforms

Same intent, the vendor's base.

Each platform starts from its own vendor's bootc image — never a derived one — and says what has actually been verified on it. What is not measured is written as not measured.

PlatformBaseComposesImageBootedPublished
CentOS Stream 10 centos-bootc validated CI GNOME + session quay.io/deskos
AlmaLinux 10 almalinux-bootc validated CI GNOME + session quay.io/deskos
Fedora 45 fedora-silverblue validated CI CI, prerelease none
RHEL 10 rhel-bootc validated by the org by the org never

RHEL-derived images are never published. Fedora is pinned to a prerelease compose; when the released compose lands, the pin moves and the measurement is repeated.

03 What the plan carries

Packages, not a script

Package groups, individual packages, signed third-party repositories, RPM files with a checksum and a key. No postInstall, no shell hook.

Desktop defaults

Wallpaper, login logo, shell extensions, dock, keyboard. Written as dconf defaults, never as locks: a user can still change them.

Boot and update policy

Kernel arguments, Plymouth theme, and the units that stage updates. The platform's own update timer is masked so there is exactly one path.

Trust and evidence

CA anchors, Flatpak remotes and a declared SBOM. The published digest is signed and attested; the installed SBOM is scanned before the tag moves.

04 Install

Take the image,
or build one.

The community images are published as bootable containers. Pull one, write a disk or an installer ISO, boot it. RHEL 10 is built and published by the organization that is entitled to it.

Installer ISOs for the community images are in progress: the build, the install test and the download site are being prepared. Until then, the documented path is the image and bootc-image-builder.

05 Questions

Before you ask.

Is this a distribution?

No. DeskOS compiles workstations onto the base each vendor already ships. It does not own a kernel, a package archive or a support contract for one.

What does "deterministic" mean here, exactly?

The compiler is offline and its output is a pure function of the resources: same inputs, same plan and same Containerfile. The image build is not bit-for-bit reproducible yet — external repositories move — and the documentation says so.

Do I need RHEL to use it?

No. CentOS Stream 10 and AlmaLinux 10 are subscription-free and are published here. RHEL 10 is supported as a platform, but its builds stay with the organization that holds the entitlement.

Why no configuration management agent?

The artifact is the delivery. What a machine runs is decided when it is compiled, reviewed as a diff, and pinned by digest. There is no reconciliation loop to drift.

Where are the ISOs?

Being built. The pipeline compiles them from a published digest, installs them in a VM to prove they work, signs the checksum and serves them from a download host. They will appear on this page when that evidence exists.
